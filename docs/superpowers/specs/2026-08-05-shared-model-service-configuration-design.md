# Qwen Local 与 MemOS 共享模型配置及按需生命周期设计

状态：已批准，待实施
日期：2026-08-05
适用目录：`D:\codex\experiments\memos-local-codex`

## 1. 这份设计解决什么问题

Qwen Local 已从早期模型升级为当前的 Qwen3.5-9B Q6_K，并完成了模型复用、运行参数设置和退出选择等多轮优化。MemOS 也通过本地 MCP 接入 Codex，并复用同一个 `llama-server` 接口。

当前故障不是新模型本身不可用，而是两个消费者的配置来源和生命周期没有完全统一：

- Qwen Local 从 `local-chat/data/settings.json` 读取当前模型、端口和启动参数；
- MemOS 的 `scripts/mcp-server.mjs` 仍在源码中写死旧模型文件和部分启动参数；
- Qwen Local 可以按用户选择停止共享模型；
- 已经启动的 MemOS MCP 只在进程初始化时检查一次模型，此后模型被停止时，记忆调用会直接访问已失效的端口；
- MemOS 想重新启动模型时，硬编码的旧模型文件已经不存在，无法按当前部署恢复。

结果是：Qwen Local 能正常使用新模型，但 MemOS 可能处于“配置仍启用、MCP 进程仍存在、模型端点已经停止”的半失效状态。

### 2.2 Qwen Local 已有的生命周期能力

现行实现已经具备以下行为，本设计必须保留：

1. 启动时先检查配置端口上的健康服务，健康时直接复用，不重复加载模型。
2. 区分“当前窗口启动的模型”和“外部已存在、当前窗口复用的模型”。
3. 退出时提供三个明确选择：
   - 停止模型并退出；
   - 仅退出软件；
   - 取消。
4. 即使模型是复用的，用户也可以明确选择停止；停止前会核验监听进程确实是配置的 `llama-server.exe`。
5. 端口被其他不健康进程占用时不杀进程、不强行覆盖。
6. Qwen Local 内部启动 MemOS 时仍设置 `MEMOS_REUSE_LLM_ONLY=1`。该旧开关能避免同一窗口重复加载第二份模型，但会在模型停止后永久禁止该 MCP 子进程按需恢复，与本设计确认的按需唤醒语义冲突，实施时需要由共享配置与跨进程锁替代。
7. 修改需要重启的模型参数时：若当前窗口拥有模型，则可重启；若只是复用，则提示下次重启模型后生效。

### 2.3 已观察到的 MemOS 行为

- 2026-08-05 18:07 的后台记忆处理访问 `127.0.0.1:18135` 失败。

- MemOS MCP 进程仍有残留，但其启动时依赖的模型服务已经结束。

## 4. 目标与非目标

### 4.1 目标

1. 建立单一、可校验、可迁移的本地模型服务配置。
2. Qwen Local 继续作为主要的可视化设置与退出控制界面。
3. MemOS 在真实记忆调用发生时能够复用或按需启动当前配置的模型。
4. 防止 Qwen Local 与 MemOS 并发启动两份模型。
5. 保持仅本机回环、无云端回退、无隐式密钥继承的隐私边界。
6. 更换模型、端口或启动参数后，无需修改消费者源码。
7. 配置错误时给出可操作错误，不静默使用旧模型或不明默认值。

### 4.2 非目标

1. 不新增常驻 Windows 服务。
2. 不重写 Qwen Local 已经稳定的 C# 模型管理器。
3. 不把 MemOS 数据库、聊天设置和模型服务设置合成一个大配置文件。
4. 不开放非回环监听。
5. 不允许 MemOS 自动修改 Qwen Local 的生成偏好。
6. 不在本次改造中更换模型、量化版本或 llama.cpp 运行时。

## 5. 方案比较

### 方案 A：共享配置，保留两端现有管理逻辑

Qwen Local 继续使用 `QwenServiceManager`；MemOS 启动器改为读取同一共享配置，并增加按需恢复和跨进程互斥。

优点：

- 对现有 Qwen Local 改动最小；
- 保留已经验证的 UI、退出选择和进程路径核验；
- 能直接消除模型文件和端口硬编码；
- 出现回归时边界清楚。

代价：

- C# 与 Node.js 仍各自保留一部分健康检查和进程启动代码；
- 必须用同一配置合同和跨进程锁保证行为一致。

### 方案 B：共享配置，加统一模型管理命令

新增一个本地命令统一提供 `status`、`ensure` 和 `stop`，Qwen Local 与 MemOS 都调用该命令。

优点：模型启动和停止逻辑只有一份。

代价：需要让成熟的 Qwen Local 生命周期依赖新的外部命令，改动和回归面明显扩大。

### 方案 C：常驻模型管理服务

新增长期运行的模型服务管理进程，两个消费者只发控制请求。

优点：集中管理最彻底，适合更多客户端共享。

代价：引入服务安装、启动、恢复和权限维护；当前单机双客户端场景不需要这层复杂度。

### 推荐

采用方案 A。当前问题来自配置和恢复边界，不需要替换 Qwen Local 已经可靠的生命周期实现。

## 6. 推荐架构

```text
Qwen Local 设置界面
        │ 读取 / 校验 / 保存
        ▼
共享模型配置（唯一配置真值）
        ▲                 ▲
        │                 │ 每次 ensure 时重新读取
QwenServiceManager    MemOS MCP 启动器
        │                 │
        └──────┬──────────┘
               ▼
     跨进程启动锁 + 回环端口检查
               ▼
       单个 llama-server 进程
               ▼
      127.0.0.1:<配置端口>
```

职责划分：

- 共享配置：保存模型服务启动合同。
- Qwen Local：编辑配置、启动/复用模型、展示状态、处理退出选择。
- MemOS MCP：在需要 LLM 的记忆调用前复用或按需启动模型。
- `llama-server`：只负责模型推理，不保存配置真值。
- MemOS `runtime/config.yaml`：继续保存 MemOS 算法、存储和 LLM 客户端策略；模型端点与别名在运行时由共享配置覆盖，不能再成为第二份人工维护值。

## 7. 共享配置合同

### 7.1 建议位置

建议使用：

`D:\codex\experiments\memos-local-codex\runtime\model-service.json`

原因：

- 它是本机部署配置，不适合提交到公共仓库；
- Qwen Local 和 MemOS 都能从共同项目根稳定定位；
- 与模型、数据库和日志同属本机运行边界；
- 路径字段可以相对项目根保存，减少机器绑定。
- 正式实现允许测试通过专用环境变量覆盖共享配置路径，但生产运行不依赖环境变量拼装模型字段。
- 仓库可保存不含机器路径和私有数据的 `model-service.example.json`；真实 `runtime/model-service.json` 必须加入忽略规则。

### 7.2 建议结构

```json
{
  "schema_version": 1,
  "bind_host": "127.0.0.1",
  "port": 18135,
  "server_executable": "llama\\bin\\llama-server.exe",
  "model_path": "models\\Qwen3.5-9B-Uncensored-HauhauCS-Aggressive-Q6_K.gguf",
  "model_alias": "qwen3.5:9b-uncensored-local",
  "context_size": 8192,
  "gpu_layers": 99,
  "parallel_slots": 1,
  "reasoning_enabled": true,
  "use_jinja": true,
  "startup_timeout_seconds": 180,
  "auto_start_on_demand": true
}
```

### 7.3 配置归属

属于共享配置的字段：

- 回环地址和端口；
- `llama-server` 可执行文件；
- 模型文件和模型别名；
- 上下文、GPU 层、并发槽位；
- 推理模式、Jinja；
- 启动超时；
- 是否允许按需启动。

仍属于 Qwen Local 聊天设置的字段：

- 温度、惩罚参数、最大输出；
- 历史轮数、长文策略、流式设置；
- 会话排序；
- 是否使用 MemOS、召回数量；
- 是否保存聊天日志。

仍属于 MemOS 配置的字段：

- embedding 模型；
- 存储、FTS、记忆算法；
- 遥测和日志策略；
- LLM 调用温度、重试和超时策略。

## 8. 配置读取、保存与生效

1. Qwen Local 启动时读取共享配置，再读取自身聊天设置。
2. 设置界面仍可以编辑模型字段，但模型字段保存到共享配置。
3. 聊天设置不再保存模型字段；迁移期间只允许读取旧字段，不再双写。
4. MemOS 每次执行模型 `ensure` 前重新读取共享配置，避免长期 MCP 进程缓存旧路径。
5. 不需要重启模型的聊天参数按现有规则即时或下次请求生效。
6. 模型文件、端口、上下文等启动参数修改后，继续使用现有提示：拥有模型时可重启；复用模型时等待用户停止后再按新配置启动。
7. 写配置采用临时文件、落盘和原子替换，禁止产生半个 JSON。
8. 共享配置必须带 `schema_version`；遇到未知版本时停止使用并报告，不猜测字段含义。
9. MemOS 启动 `llama-server` 时，`reasoning_enabled`、`use_jinja`、`parallel_slots`、上下文、GPU 层、端口、别名和模型文件全部来自共享配置；任何一项都不得在启动器中保留第二套固定值。

## 9. 模型生命周期

### 9.1 Qwen Local 启动

1. 读取并校验共享配置。
2. 检查回环端口健康状态。
3. 健康且服务身份符合配置时复用。
4. 不健康且端口空闲时取得跨进程启动锁，再次检查健康状态。
5. 仍无服务时按共享配置启动一个模型。
6. 端口被不健康进程占用时停止自动启动并显示错误，不杀占用进程。

### 9.2 MemOS 调用

`memos_recall` 和 `memos_remember`：

1. 调用前读取共享配置。
2. 模型健康时复用。
3. 模型停止且 `auto_start_on_demand=true` 时，取得跨进程锁并按需启动。
4. 模型启动完成后再进入记忆流程。
5. 启动失败时返回明确错误，不调用云端服务。
6. 旧的 `MEMOS_REUSE_LLM_ONLY` 硬禁止不再决定能否启动；统一执行“健康检查 → 原子锁文件 → 重新读取配置 → 按 `auto_start_on_demand` 决策”的流程。

`memos_health` 和 `memos_list_recent`：

- 保持只读；
- 不因健康检查或读取历史而启动模型；
- `health` 应分别报告 MemOS 核心、embedding、模型端点和配置状态。

### 9.3 Qwen Local 退出

- “停止模型并退出”：停止当前配置端口上的已验证 `llama-server`，释放资源后退出。
- “仅退出软件”：保留模型，MemOS 可以继续复用。
- “取消”：返回应用。
- 选择停止后不立即由后台健康检查重新启动；只有后续允许启动的真实记忆调用可以重新启动。

### 9.4 并发启动

仅有进程内 `SemaphoreSlim` 或 JavaScript 变量不足以阻止两个程序同时启动模型。需要增加跨进程互斥：

- 主路径使用运行目录内带 PID 的原子锁文件，使 C# 与 Node.js 遵循完全相同、可观察的合同；
- 锁文件记录创建者 PID、创建时间、客户端类型和配置语义摘要，不记录提示词、记忆正文或令牌；
- C# 可以额外使用命名互斥体降低同进程族竞争，但命名互斥体不能替代锁文件合同；
- 取得锁后必须再次检查健康状态；
- 超时锁只能在确认创建者进程不存在后回收；
- 启动结果以端口健康和服务身份为准，锁文件不是服务真值。

### 9.5 锁文件合同

固定路径：

`runtime/locks/model-service-start.lock`

固定内容：

```json
{
  "schema_version": 1,
  "owner_pid": 12345,
  "owner_client": "qwen-local",
  "acquired_at": "2026-08-05T12:00:00Z",
  "config_sha256": "共享配置规范化内容的 SHA-256"
}
```

合同要求：

1. C# 使用 `FileMode.CreateNew`，Node.js 使用等价的排他创建模式；只有原子创建成功者取得启动权。
2. `owner_client` 只允许 `qwen-local` 或 `memos-codex` 等登记值，不接受任意用户输入。
3. 等待方按有界间隔检查服务健康状态和锁拥有者进程，不进行无界等待。
4. 只有拥有者 PID 已不存在且服务仍不健康时，才允许回收过期锁。
5. 启动成功、确认他方已经启动成功或启动失败后，锁拥有者都必须释放锁。
6. 锁文件不得保存完整模型路径、命令行、提示词、记忆正文或环境变量。

## 10. 服务身份与安全边界

仅返回 HTTP 200 的 `/health` 不足以证明端口上运行的是目标模型。复用前建议验证：

1. 监听地址必须是 `127.0.0.1` 或 `::1`。
2. 监听进程路径与共享配置中的 `llama-server.exe` 都解析为规范化绝对路径后，使用 Windows 不区分大小写的路径语义比较。
3. 服务暴露的模型别名应与共享配置一致；如果接口不能可靠提供别名，身份状态标记为 `partial` 并明确报告，不能据此误杀服务。
4. 停止服务前必须再次核验进程路径。
5. 删除 `OPENAI_API_KEY`、`ANTHROPIC_API_KEY` 和 `MEMOS_API_KEY` 的现有保护继续保留。
6. `fallbackToHost` 和云端回退保持关闭。
7. `bind_host` 只允许回环地址；即使配置文件被修改为公网地址，也必须拒绝启动。

安全规则可以写在代码中，因为它们是不可放宽的约束；具体模型、端口和性能参数不能写死在代码中。

### 10.1 生命周期日志合同

固定路径：

`runtime/logs/model-service-lifecycle.jsonl`

每行是一个独立 JSON 事件，采用追加写入，至少包含：

- `schema_version`
- `event_id`
- `timestamp`
- `client`
- `action`：`ensure`、`reuse`、`start`、`stop` 或 `recover_lock`
- `reason`：前台记忆调用、Qwen Local 启动、用户退出选择等受控枚举
- `result`：`success`、`failed`、`partial` 或 `skipped`
- `pid` 与 `port`
- `server_path_sha256`
- `model_path_sha256`
- `config_sha256`
- 失败时的稳定 `error_code`

日志禁止包含：提示词、回复、记忆正文、聊天内容、明文完整路径、API Key、环境变量和值不受控的异常对象。面向用户的错误信息可以单独显示规范化后的必要路径，但不能直接写入生命周期日志。

## 11. 故障处理

| 情况 | 要求行为 |
|---|---|
| 共享配置不存在 | 进入一次性迁移；没有可迁移来源时报告缺失，不猜测模型文件。 |
| JSON 损坏或字段非法 | 指明文件和字段，拒绝启动；保留原文件用于恢复。 |
| 模型文件不存在 | 报告解析后的完整路径，不回退到旧模型。 |
| 可执行文件不存在 | 报告完整路径，不尝试下载或调用其他运行时。 |
| 端口空闲 | 允许取得锁后按需启动。 |
| 端口被健康目标服务占用 | 复用。 |
| 端口被不健康或身份不符的进程占用 | 拒绝启动和停止，报告 PID 与边界原因。 |
| 启动过程中另一个客户端先启动成功 | 第二个客户端复用，不能再启动一份。 |
| 模型在 MCP 长期运行期间被停止 | 下一次允许启动的真实调用重新读取配置并按需恢复。 |
| 按需启动失败 | 当前记忆调用失败或按现有 Qwen Local 策略降级为无记忆；不得云端回退。 |
| 配置版本高于客户端支持版本 | 明确提示客户端过旧，不按旧结构解释。 |

## 12. 迁移设计

建议一次性迁移顺序：

1. 读取现有 `local-chat/data/settings.json`。
2. 提取模型服务字段，校验当前模型文件与可执行文件。
3. 备份原设置文件和 MemOS 启动器相关配置。
4. 写入共享配置并重新读取验证。
5. Qwen Local 保留旧模型字段的读取兼容，用于旧安装迁移；新保存不再双写。
6. MemOS 删除源码中的具体模型文件、别名、端口和启动参数。
7. MemOS `runtime/config.yaml` 的 endpoint/model 在运行时由共享配置覆盖，不再由人工维护或另行生成。
8. 迁移完成后生成不含敏感内容的回执，记录来源、目标、配置摘要和验证结果。

不建议通过把 Q6 模型复制或改名成旧 Q4 文件名来兼容。该做法会隐藏配置错误，并使名称、量化版本和实际文件不一致。

## 13. 测试与验收

### 13.1 配置测试

- 共享配置可正确读取、保存和原子替换。
- 相对路径按项目根解析，Windows 路径大小写和分隔符正确处理。
- 非回环地址、非法端口、空别名、缺失文件和未知版本被拒绝。
- 源码中不再出现具体 Qwen 模型文件名作为启动依赖。
- Qwen Local 聊天配置与模型服务配置不再双写。

### 13.2 生命周期测试

- 无模型时打开 Qwen Local，只启动一个模型。
- 模型已由 MemOS 启动时打开 Qwen Local，显示“已复用”。
- 两端并发调用 `ensure`，最终只有一个 `llama-server`。
- “仅退出软件”后端口仍健康。
- “停止模型并退出”后进程和端口消失。
- 停止后执行 `memos_recall`，模型按共享配置重新启动并返回结果。
- `memos_health`、`memos_list_recent` 在模型停止时不启动模型。
- 配置更换为另一合法模型后，下一次启动使用新文件，不修改源码。
- 端口身份不符时不复用、不误杀。

### 13.3 MemOS 验收

- `memos_health` 分项状态符合预期。
- 使用已有真实记忆完成一次同义召回。
- 新建一条隔离验收记忆，确认写入、召回、数据库和日志边界后再清理。
- 验证没有非回环监听、没有云端请求、没有第二个模型进程。
- 验证模型停止后显存和监听释放。
- 验证 Codex、Qwen Local 分别启动的 MCP 子进程能正确退出，不遗留孤儿进程。
- 验证后台重评分、维护重试和只读查询不会单独唤醒模型；只有前台 `recall`、`remember` 等真实 LLM 需求允许按需启动。

### 13.4 回归测试

- Qwen Local 现有单元测试、UI 行为测试和设置测试全部通过。
- MemOS 现有 smoke test 和数据库完整性检查通过。
- 退出提示三种选择的文案和行为保持一致。
- 会话、流式生成、并发槽位和 MemOS 开关不受配置拆分影响。

## 15. 实施边界

在本设计得到最终批准前，不修改生产配置、不重启模型、不清理残留进程，也不执行 `git init`。

设计批准后的实施应分为四个可独立验收的阶段：

1. 建立本地 Git 与回滚基线；实现共享配置合同、读取器、校验器和迁移测试。
2. Qwen Local 接入共享配置，同时保持现有 UI 与退出行为。
3. MemOS 移除硬编码，增加按需恢复和跨进程互斥。
4. 双客户端真实联调、隐私边界检查和残留进程检查。

任何阶段失败都应保持原配置可恢复，不以复制、改名模型文件或启用云端回退作为临时修复。
